Les comptes qui manquent

Le schéma actuel sait tout d'un résident et rien de celui qui le soigne. Douze tables décrivent des corps, aucune ne décrit un soignant — donc aucune écriture n'est signée. Voici les trois tables à ajouter et les deux colonnes à poser dans l'existant.

Sola · Horizon 2080 · suite de « Du template au schéma » · proposition, rien n'est écrit en base

Ce que personne ne signe

01 La console écrit sans auteur. Depuis qu'on a retiré le jeton du formulaire de note, n'importe qui atteignant le serveur peut ajouter une ligne au dossier d'un résident. La note est horodatée ; elle n'est attribuée à personne.
02 Le backoffice s'ouvre avec un jeton unique. Une clé partagée par toute l'équipe, rangée dans le sessionStorage du navigateur. Elle prouve qu'on connaît la clé, pas qu'on est quelqu'un — et un script injecté dans la page la lit.
03 signaux.assigne_a est du texte libre. Six valeurs distinctes dans le jeu actuel — Dr. Oyelaran, Inf. Bakker, Équipe d'intervention… — qui ne pointent sur rien. Une faute de frappe crée un septième soignant.

Les deux tables de comptes

clé ou contrainte d'unicité secret — jamais en clair colonne ordinaire

medecins

la console

Ceux qui soignent. Tous la même autorité : pas de colonne de rôle, donc pas de droit à vérifier. Être dans la table, c'est le droit.

id code · M-007 prenom nom titre · Dr. / Inf. email · unique mdp_hash actif · 0/1 cree_le derniere_connexion

titre est une étiquette d'affichage, pour que la fiche continue d'écrire « Dr. Nakamura ». Ce n'est pas un droit : un infirmier et un médecin ouvrent exactement les mêmes écrans.

admins

le backoffice

Ceux qui exploitent : corriger une donnée, réassigner un signal, regarder les tables brutes. Même forme, table séparée.

id prenom nom email · unique mdp_hash actif · 0/1 cree_le derniere_connexion

Pas de code : un administrateur n'apparaît nulle part dans une interface de soin. Il agit, il ne signe pas de note.

La troisième table : les sessions

sessions

les deux
id · sha256 du cookie medecin_id admin_id ouverte_at expire_at

Deux clés étrangères dont une seule est remplie, garanties par un CHECK. C'est ce qui rend impossible une session à cheval sur les deux tables, et ce qui fait disparaître les sessions d'un compte quand ce compte disparaît.

Ce que fait une connexion

  1. Le navigateur envoie l'e-mail et le mot de passe, une seule fois, à POST /api/connexion.
  2. Le serveur recalcule le hachage et le compare à mdp_hash, en temps constant, comme il compare déjà les jetons.
  3. Il tire 32 octets au hasard, en range l'empreinte dans sessions, et renvoie la valeur brute dans un cookie httpOnly · SameSite=Strict.
  4. Le navigateur ne voit jamais rien : aucun script de la page ne peut lire ce cookie, contrairement au jeton d'aujourd'hui.

Les partis pris

Deux tables plutôt qu'une colonne role

Une table unique avec un rôle met la séparation dans une clause WHERE, donc à portée d'un oubli. Deux tables la mettent dans le schéma : un médecin ne peut pas devenir administrateur par erreur de code, il n'est pas dans la bonne table.

WHERE role = 'admin' — une ligne à oublier
FROM admins — rien à oublier

Le mot de passe n'est jamais stocké

Seulement son empreinte, par scrypt — fourni par Node 24, rien à installer, comme SQLite. La colonne s'appelle mdp_hash et non pswd : le nom rappelle ce qu'on a le droit d'y mettre.

pswd TEXT — invite à écrire le mot de passe
mdp_hash TEXT — n'invite à rien

On désactive, on ne supprime pas

actif = 0 ferme le compte, la ligne reste. Sinon les notes signées par un soignant parti perdraient leur auteur — or une note non signée, c'est exactement le problème qu'on est en train de régler.

pas d'ON DELETE sur auteur_id : la base refuse la suppression

Les bornes gardent leur jeton

BORNE_TOKEN ne bouge pas. Une borne de cabine est une machine : elle n'a pas de mot de passe à saisir ni de session à ouvrir. Seul ADMIN_TOKEN disparaît, remplacé par la table admins.

machine → jeton  ·  personne → compte

Le SQL, d'un bloc

-- Ceux qui soignent. Tous la meme autorite : pas de colonne de role.
CREATE TABLE medecins (
  id                 INTEGER PRIMARY KEY,
  code               TEXT NOT NULL UNIQUE,          -- M-007, affiche sur la note
  prenom             TEXT NOT NULL,
  nom                TEXT NOT NULL,
  titre              TEXT NOT NULL CHECK (titre IN ('Dr.','Inf.')),
  email              TEXT NOT NULL UNIQUE,          -- range en minuscules
  mdp_hash           TEXT NOT NULL,                 -- scrypt, jamais le mot de passe
  actif              INTEGER NOT NULL DEFAULT 1 CHECK (actif IN (0,1)),
  cree_le            TEXT NOT NULL DEFAULT (datetime('now')),
  derniere_connexion TEXT
) STRICT;

-- Ceux qui exploitent. Meme forme, table separee : la separation est
-- dans le schema, pas dans une clause WHERE.
CREATE TABLE admins (
  id                 INTEGER PRIMARY KEY,
  prenom             TEXT NOT NULL,
  nom                TEXT NOT NULL,
  email              TEXT NOT NULL UNIQUE,
  mdp_hash           TEXT NOT NULL,
  actif              INTEGER NOT NULL DEFAULT 1 CHECK (actif IN (0,1)),
  cree_le            TEXT NOT NULL DEFAULT (datetime('now')),
  derniere_connexion TEXT
) STRICT;

-- L'id stocke est l'EMPREINTE du cookie, pas le cookie : une copie de la
-- base ne donne aucune session ouverte. Le CHECK garantit qu'une session
-- appartient a un medecin OU a un admin, jamais aux deux.
CREATE TABLE sessions (
  id         TEXT PRIMARY KEY,                      -- sha256 du jeton du cookie
  medecin_id INTEGER REFERENCES medecins (id) ON DELETE CASCADE,
  admin_id   INTEGER REFERENCES admins   (id) ON DELETE CASCADE,
  ouverte_at TEXT NOT NULL DEFAULT (datetime('now')),
  expire_at  TEXT NOT NULL,
  CHECK ((medecin_id IS NULL) <> (admin_id IS NULL))
) STRICT;

CREATE INDEX idx_sessions_expire ON sessions (expire_at);

-- Les deux colonnes dans l'existant. Pas d'ON DELETE sur auteur_id :
-- la base doit refuser d'effacer un medecin qui a signe des notes.
ALTER TABLE particularites ADD COLUMN auteur_id  INTEGER REFERENCES medecins (id);
ALTER TABLE signaux        ADD COLUMN assigne_id INTEGER REFERENCES medecins (id);

Ce qui reste à trancher

Le premier compte. Il faut un compte pour en créer un, et au premier démarrage il n'y en a aucun. Le plus simple : une commande npm run compte:admin qui en crée un depuis le terminal — physiquement sur le vaisseau, donc pas exposée sur le réseau.
Le mot de passe oublié. Sans messagerie à bord, pas de lien de réinitialisation. Un administrateur remet un mot de passe provisoire, et la session suivante oblige à le changer — reste à décider si on modélise ce « provisoire » (une colonne) ou si on l'assume à l'oral.
Le nombre d'essais. Rien ne ralentit aujourd'hui un essai de mots de passe en rafale. Un compteur par compte, ou un délai par adresse : les deux tiennent en quelques lignes, mais ce n'est pas la même colonne.
Le journal d'audit. auteur_id signe les notes, assigne_id signe les affectations. Tout le reste — un statut corrigé, un signal clos — reste anonyme. Une table journal le règlerait, mais c'est un autre lot.
Proposition, pas encore appliquée : aucune de ces tables n'existe dans db/serveur/01-schema.sql. Trois tables, deux colonnes, deux routes de connexion — c'est le plus petit ensemble qui permette d'écrire, au bas d'une note de dossier, le nom de la personne qui l'a écrite.
